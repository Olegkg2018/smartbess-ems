## 1a. Механизм заявок РДН (реализовано 2026-07-31, расширено 2026-08-06)

Раньше весь проект (MILP, бэктест, отчётность) неявно предполагал, что запланированный график заряда/разряда исполняется всегда ровно по спрогнозированной цене — реальный механизм аукциона РДН (заявка → неизвестность до результатов аукциона → факт исполнения) нигде не моделировался. Реализовано по прямому запросу пользователя:

- **Механика (аукцион единой цены)**: заявка на продажу исполняется, если наша цена ≤ факт-цена OREE — и тогда продаём именно по факт-цене (не по своей заявленной). Заявка на покупку исполняется, если наша цена ≥ факт-цена — покупаем по факт-цене. Если не исполнилась — физически не можем зарядить/разрядить в этот час через РДН.
- **Маржа** (`BidMarginOverride`, одно значение на сутки, UI — рядом с вводом SoC на Optimization Schedule, по просьбе пользователя; лейбл в UI — «Відсоток буфера безпеки (Safety Buffer %)», переименовано 2026-08-04 по просьбе пользователя для ясности, `margin_pct`/эндпоинты/переменные в коде не переименовывались): двигает цену заявки от прогноза в сторону большей вероятности исполнения — продажа: прогноз×(1-маржа%), покупка: прогноз×(1+маржа%). Маржа 0% = подавать ровно по прогнозу (макс. риск неисполнения при ошибке прогноза).
- **Легальні межі ціни заявки OREE (2026-08-06)**: `clamp_bid_price_to_oree_bounds` (`bidding_service/services.py`) обмежує обчислену ціну заявки в 10.00–50000.00 грн/МВт·год (реальні межі, НЕ бізнес-`PRICE_CAP=16000.0` з `ml_pipeline.py`) — застосовується в `generate_bids_for_date` після формули маржі; реальний кейс: прогноз біля floor + висока маржа могли дати ціну поза законними межами без жодного попередження. Прапорець `bid_price_legally_clamped` обчислюється на льоту (не нова колонка БД), UI показує попередження (`AlertTriangle`).
- **ВДР-фолбэк**: если заявка РДН не сыграла, предлагается альтернатива на ВДР — оценка цены через `ml_pipeline.estimate_idm_price_for_hour` (та же методология медианной разницы, что и для заполнения хвоста `IDM_Price_Lag_24`), т.к. реальной цены ВДР на этот час ещё нет (ВДР ближе к реальному времени поставки, чем момент публикации результатов аукциона РДН).
- Таблицы: `MarketBid` (заявка/факт/статус/реализованный P&L/ВДР-предложение), `BidMarginOverride`. Сервис: `src/modules/bidding_service/services.py`. Роутер: `/api/v1/bids`.
- **«Центр дій» диспетчера (2026-08-06)**: `build_daily_action_summary(db, asset, target_date)` — синтезований, тільки-читання список конкретних дій на дату (сформувати заявки / подати вручну до 12:00 / перевірити ціну, скориговану до межі OREE / для кожної незіграної години — скільки і за якою ціною подати на ВДР). Ендпоінт `GET /api/v1/bids/action-summary`. НІКОЛИ сама не генерує/не звіряє заявки — читає лише вже наявний стан `MarketBid`, щоб не перетворитись на приховану автоматизацію (яку користувач явно відклав, див. §8).
- **Не сделано (сознательно, по словам пользователя — «в будущем»)**: автоматическая подача заявки через API в кабинет OREE. Сегодня это делает диспетчер вручную, глядя на цифры этой системы. Telegram-нагадування (`check_and_send_bid_reminder`, джоба 10:00) лише НАГАДУЄ на основі вже наявних заявок, не генерує і не подає їх сама.
- **Абсолютний буфер `margin_uah` (2026-09-08)** — друга опція поряд із `margin_pct`, за прямим прохідним запитом користувача після дослідження реальних 323 звірених заявок на VPS (29.07-08.09.2026): при дефолтних 2% виконується лише ~68-71% заявок, і причина структурна, не в числі 2% — купівля кластеризується біля НИЗЬКИХ цін (денний профіцит), продаж — біля ВИСОКИХ (вечірній пік), тож та сама абсолютна похибка прогнозу в ₴ вимагає для купівлі багаторазово більшого відсотка, ніж для продажу (реальні дані: щоб досягти ~90-95% виконання відсотковим буфером, купівлі потрібно ~98.5%, продажу — лише ~22%). Оскільки розрахунок завжди йде за факт-ціною (аукціон єдиної ціни, вище), розширення буфера не коштує прямого прибутку (крім легальних меж OREE) — стеля виконання визначається лише непередбачуваними ціновими викидами. `margin_uah` (₴/МВт·год, `sell=forecast-margin_uah`, `buy=forecast+margin_uah`) дає набагато рівномірніший результат для обох напрямків — реальні дані вказують ~2000-2500 ₴/МВт·год для ~90-95% з обох боків. `NULL` (дефолт) = стара відсоткова поведінка без жодної зміни; коли задано — має пріоритет над `margin_pct` у `generate_bids_for_date`, `margin_pct` рядка `MarketBid` стає лише еквівалентним відсотком для відображення. UI — селектор режиму поряд із існуючим полем маржі на Optimization Schedule. Див. CLAUDE.md п.52.
- **Небаланс з балансуючим ринком (БР) — 2026-09-09.** Реальний обліковий Excel справжнього підприємства з батареєю (наданий користувачем) показав повну формулу звірки: дефіцит/профіцит між тим, що РЕАЛЬНО пройшло через лічильники (Факт Заряд/Розряд/**Власні потреби батареї**), і тим, що заявлено на РДН+ВДР, закривається на БР за реальною (не похідною від РДН) ціною. Підтвердило раніше обговорену з користувачем гіпотезу "власних потреб" прямим числом з реального файлу: навіть у "тиху" добу без жодної РДН/ВДР-активності постійне власне споживання (контролер/охолодження) створює маленький дефіцит щогодини. Реалізовано: `MarketBid` отримав 5 nullable-полів (Факт-показники + ціни БР, диспетчер вводить вручну після отримання реального рахунку звірки — офіційного живого джерела цих даних немає, MEMORY.md §6a п.13 "Розвідка небалансу заблокована"), `compute_imbalance_financials` рахує обсяг/вартість небалансу за формулою з реального файлу, новий ендпоінт `POST /bids/actual-settlement` (уся доба одним запитом), нова картка "Небаланс та звірка з БР" на Optimization Schedule, +10 колонок у Excel-звіті за період. Див. CLAUDE.md п.57.
- **Важная связь с §2/п.3 (perfect foresight ratio) — доведено до конца 2026-07-31.** `compute_real_profit_capture_ratio` теперь для каждой полной сутки сначала проверяет, есть ли за неё полностью звiренные `MarketBid` (все 24 часа с заполненным `executed`) — если да, `actual_profit_uah` = сумма `MarketBid.realized_profit_uah` (честный ноль за часы, где заявка не сыграла на РДН; ВДР-фолбэк намеренно НЕ засчитывается как реализованный, т.к. это лишь предложение диспетчеру, а не гарантированное действие — автоподача в кабинет OREE не реализована, см. п.9). Для суток старше появления механизма заявок (до 2026-07-31) — прежний фолбэк через `ChargeDischargePlan` × реальную цену (неявно предполагает 100%-исполнение), с явной пометкой источника (`market_bid_settled` vs `chargedischargeplan_full_execution_assumed`) на каждый день и агрегированным счётчиком `n_days_market_bid_settled`/`n_days_plan_full_execution_assumed` в ответе API и на `ForecastAccuracy.tsx`. Проверено на локальной dev-БД: день 2026-07-06 (единственный с полными 24 звiренными заявками) корректно попал в новую ветку, сумма realized_profit_uah = 1948.05 грн.

## 2. Решения для расчёта

- **Прогноз цены**: LightGBM как продовая модель (300 estimators, max_depth 7, lr 0.06); XGBoost и MLP считаются параллельно, доступны только при ручном запуске прогноза (не используются в ежедневной автоматической джобе).
- **Интервал неопределённости**: отдельная LightGBM quantile-регрессия (α=0.1/0.9) + split-conformal калибровка на последних 60 днях held-out — даёт честное ~80%-покрытие на реальных данных, а не теоретическое.
- **MILP-оптимизация** (`milp_model.py`, PuLP/CBC): решение на горизонте T часов (обычно 24), бинарная переменная заряд/разряд на час, ограничение цикла (`max_cycles_per_day`, настраивается 0.5–5.0), финальный SoC = min_soc (батарея должна разрядиться к концу суток). Режимы: `arbitrage` (FTM, продажа по чистой DAM-цене) vs `self_consumption` (BTM, продажа тоже с тарифами).
- **Risk-сценарии**: Pessimistic/Aggressive строятся на реальных P10/P90 модели, если доступны (`band_source='quantile_model_p10_p90'`), иначе — фолбэк на теоретическое допущение ±1.64σ (`assumed_volatility`, volatility=0.18 по умолчанию). Monte Carlo VaR (95%, 30 симуляций) использует погодинную (гетероскедастичную) волатильность, выведенную из реальной ширины P10/P90-полосы, а не константу.
- **Ручная поправка генерации** (`GenerationAdjustment`): Solar/Wind % напрямую масштабируют реально обученные фичи Solar_Gen/Wind_Gen; Nuclear/Hydro % (нет данных по типам генерации с 2022, см. §5) конвертируются в дельту МВт через справочные мощности (7835 МВт АЕС / 3800 МВт ГЕС по умолчанию, редактируются в Settings), масштабируются коэффициентом `baseload_passthrough_ratio` (default 0.3 — не весь дефицит АЕС/ГЕС проявляется в трансграничном потоке, часть поглощается внутри страны) и жёстко ограничиваются реальным 99-перцентилем `Grid_Net_Export_MW` за последние 180 дней, прежде чем добавиться к реально обученной фиче Grid_Net_Export — приближённо, но не выдумано: дельта проходит через уже обученную моделью зависимость цены от нетто-экспорта, и не выталкивает фичу за пределы обучающего распределения. **Найдено и исправлено 2026-08-03**: без ratio+clip справочные мощности (7835/3800 МВт) на порядок превышали реальный разброс Grid_Net_Export_MW (std≈392 МВт) — уже при 20-30% отклонения дельта выходила за пределы того, на чём LightGBM обучался, и прогноз переставал реагировать вовсе (деревья не экстраполируют). Отдельно исправлен workflow-разрыв: сохранение `GenerationAdjustment` теперь само триггерит пересчёт `PriceForecast`, если он уже существует на эту дату (см. CLAUDE.md, пункт 10 хронологии).
- **Ручной зсув прогнозу ціни** (`PriceShiftOverride`, добавлено 2026-08-03) — отсоткова поправка на конкретну дату для випадку реальной тимчасовой ринковой аномалии (напр. гравець коротко манипулировал/занижал цену, вже откачено), яку модель не могла передбачити и НЕ варто вчити з одного эпизода. Принципово иначе, чем `GenerationAdjustment` (вище): применяется ПІСЛЯ передбачення моделі (`predict_next_day`/`predict_price_band` в `ml_pipeline.py`) — `clip(raw, FLOOR, CAP) * (1 + shift_pct/100)`, потім повторний clip — а не як ознака, тому не заходить у проблему насичення дерев (жодна ознака не змінюється) і структурно не торкається `walk_forward_backtest`/`train_models` (вони рахують `model.predict()` напряму на історичних даних). Перевірено: `shift_pct=0` — строгий no-op (побайтово), `shift_pct=-20` дає ratio рівно 0.8 на кожну годину точкового прогнозу і P10/P90-полоси (реальний HTTP-цикл: 5536.60→4429.28 грн/МВт·год, зворотньо точно). Спільний хелпер `trigger_forecast_recompute_if_exists` (`forecast.py`) — той самий авто-тригер перерахунку, що й у `GenerationAdjustment`, винесений в один хелпер, щоб не дублювати вдруге (дублювання один раз вже призвело до бага, знайденого 2026-08-03 при `GenerationAdjustment`).
- **SoC на начало суток** — цепочка приоритетов: ручное значение (`InitialSocOverride`) → SCADA-телеметрия → расчётный конец предыдущих суток (последний час вчерашнего MILP-плана) → фолбэк 20%. Это расчётное значение из плана оптимизатора, не пересчёт с учётом фактической почасовой ручной диспетчеризации за прошлые сутки (более сложная доработка, не сделана).
- **Двухступенчатый surplus-классификатор** (`_make_surplus_classifier`/`_blend_with_surplus_proba` в `ml_pipeline.py`) — LightGBM-классификатор P(цена упадёт в профицитную "підлогу" ≤20 грн), линейно смешивается с точечным прогнозом. Реализован и доступен как флаг `use_surplus_classifier` только в `walk_forward_backtest` — **НЕ подключён** в `predict_next_day`/продовый путь. Экспериментальный, статус не финализирован.
- **Реальні тарифи участі в ринку OREE (2026-08-06)** (`TariffService.calculate_oree_participation_fee_uah`) — фіксований місячний внесок 4669.71 грн + тариф на операції 6.88 грн/МВт·год (тариф 2026, `oree.com.ua/index.php/newsctr/n/30795`). ## 4. Проверенные варианты улучшения прогноза — что дало эффект, что нет

Методология: `walk_forward_backtest(test_days=60-90, retrain_every_days=7)` на данных 2021–2026, сравнение `mean_wape` (общая точность) и особенно `last_7d_mean_mape`/`last_30d_mean_mape` (последние/волатильные дни — то, что реально нужно улучшить). Все решения ниже задокументированы прямо в комментариях `ml_pipeline.py`/`neighbor_weather.py`/`entsoe.py`, не только в истории чата.

**КРИТИЧНА методологічна знахідка (2026-09-08)**: `extra_features=[...]` вимикає as-of-уніфікацію (`asof_eligible = ... and not extra_features`), тож кандидат завжди йде через LEGACY-шлях (`methodology_version: phase_b_leakage_fix_only_2026`), а бейзлайн без `extra_features` — через РЕАЛЬНИЙ прод-шлях (`phase_b_asof_unified_2026`). **Ці два шляхи систематично дають РІЗНІ числа на ОДНОМУ Й ТОМУ Ж вікні незалежно від кандидата** — підтверджено контрольним тестом: `extra_features=['Grid_Stress_High']` (реальний сигнал) дав mean_wape 26.19%, а контроль `extra_features=['Grid_Stress_Medium']` (свідомо БЕЗ сигналу — константний нуль у цьому вікні, той самий legacy-шлях) дав mean_wape 26.01% — тобто МАЙЖЕ ІДЕНТИЧНО кандидату і **суттєво краще за as-of-бейзлайн (30.00%)**, попри нульову інформацію. Різниця бейзлайн↔кандидат, яку раніше приписували самій фічі (EU_DAM_Price, PL/RO погода, Imbalance_Price/Grid_Outage_Official — усі тестувались через `extra_features`), могла суттєво складатись із цього самого зсуву шляху, не лише з реального ефекту фічі. **Правило на майбутнє: НІКОЛИ не порівнювати `extra_features`-кандидата напряму з as-of-бейзлайном** — спершу прогнати контроль (`extra_features=['якась_завідомо_нульова_або_шумова_колонка']`) на тому самому вікні, і порівнювати кандидата ЛИШЕ з цим контролем, не з прод-бейзлайном.

**Важная оговорка (актуальна для строк ДО 2026-08-21)**: до этой даты `walk_forward_backtest` был отдельной реализацией (`prepare_features`), которая физически никогда не пересекалась с продовым инференсом (`build_forecast_feature_matrix`) и имела утечку данных (см. `docs/review_ml_forecast_pipeline_2026-08-21.md`, Фаза B). Новый честный as-of-бектест (Фаза B, тот же вечер) реально вызывает прод-код — Фаза C (2026-08-21) повторно перепроверила ключевые решения ниже на нём: **Lag_48 подтверждён отклонённым ещё увереннее** (хуже по всем трём метрикам, не только по last_7d/30d), EU_DAM_Price/PL-RO-погода остаются отклонёнными (паттерн "last_7d хуже" сохранился и после устранения утечки — это аргумент, что находка была реальной, не артефактом старого бектеста), ансамбль показал более устойчивый сигнал улучшения last_30d (-17%), чем раньше — не подключён, но кандидат для отдельного рассмотрения. Полные новые цифры — `docs/review_ml_forecast_pipeline_2026-08-21.md`, раздел «Фаза C».

**Вторая оговорка (актуальна для строк ДО 2026-08-24)**: все цифры в таблице ниже — включая Фазу C — считались до фикса Kyiv/UTC день-границ (CLAUDE.md п.26-28, см. также §6 п.8). ## 6a. Конкретные идеи из повторного рыночного исследования (2026-07-31, второй проход — open-source GitHub + фичи коммерческих платформ)

В отличие от первого прохода (§7 ниже, только общий ландшафт), в этот раз искали **конкретные, называемые фичи**, а не общие описания — чтобы получить реально внедряемые идеи, а не маркетинговые лозунги. Приоритизировано по посильности для небольшой команды и соответствию принципу проекта "сначала бэктест, потом в прод".

**Стоит рассмотреть в первую очередь:**
1. **Ставки во второй рынок (ВДР/IDM), а не только РДН** — сейчас `IDM_Price`/`DAM_IDM_Spread` в проекте используются ТОЛЬКО как фича прогноза, но не как реальный второй канал диспетчеризації. Открытый [FlexPwr/bess-optimizer](https://github.com/FlexPwr/bess-optimizer) (Pyomo/GLPK) явно показывает паттерн последовательной co-оптимизации РДН→ВДР-аукціон→ВДР-континуум (каждый рынок открывается позже и уточняет план). Коммерчески то же самое делают DYNVOLT и Arenko Nimbus (DAM+intraday+aFRR/FCR+imbalance в одном MILP, DYNVOLT заявляет +34% выручки к arbitrage-only). Для smartbess-ems это реалистичное расширение `milp_model.py`: разыгрывать часть мощности на IDM, а не только на DAM, используя уже собираемые реальные данные IDM. ([dynvolt.com/bess](https://www.dynvolt.com/bess), [arenko.group/optimisation](https://arenko.group/optimisation/))
2. **Деградация как функция DoD/throughput, а не плоская константа** — сейчас `degradation_cost` в `milp_model.py` — единое число (1.20 UAH/kWh). Habitat Energy и DYNVOLT считают маржинальную стоимость деградации по кривой глубины разряда/цикла (не постоянная), Wärtsilä GEMS Pulse — на уровне SoH ячеек. Это не экзотика — кусочно-линейные/выпуклые кривые cost(DoD) — стандартная, хорошо описанная в литературе MILP-техника (см. [обзор ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0142061521010140)), контролируемое изменение объёма работы. ([habitat.energy](https://habitat.energy/habitat-energy-launches-battery-optimization-service-in-usa/), [Wärtsilä GEMS Pulse](https://www.wartsila.com/media/news/06-08-2024-wartsila-s-seventh-generation-gems-digital-energy-platform-supports-rapid-pace-of-scale-and-change-in-global-energy-storage-industry-3480027))
3. **"% захваченной прибыли от идеального прогноза" как метрика на Director Dashboard** — GridBeyond даёт сравнение "vs perfect foresight" в UI, Ascend Analytics заявляет 90-95% от perfect foresight как продающий показатель. У smartbess-ems уже есть все кусочки (реальная цена через `/forecast/actual`, сам MILP-солвер) — не хватает только самого расчёта "что заработал бы MILP на РЕАЛЬНОЙ цене этого дня" вместо "что заработал на прогнозе". Почти бесплатное добавление. ([GridBeyond](https://gridbeyond.com/gridbeyond-launches-bid-optimizer-to-boost-batteries-profits/), [Ascend SmartBidder](https://www.ascendanalytics.com/blog/leveraging-bid-optimization-software-to-maximize-battery-energy-storage-value))
4. **Ансамбль прогнозных моделей вместо одной** — Ascend прямо называет мульти-модельный прогноз диверсификацией риска ("как портфель акций"). У smartbess-ems уже обучаются LightGBM/XGBoost/MLP в `ml_pipeline.py`, но в проде используется только LightGBM. Бэктест простого блендинга (среднее или взвешивание по обратной ошибке) — дешёвый эксперимент, полностью совместимый с уже существующим `walk_forward_backtest`. ([Ascend SmartBidder](https://www.ascendanalytics.com/blog/leveraging-bid-optimization-software-to-maximize-battery-energy-storage-value))
5. **LCOS (levelized cost of storage)** как метрика в ROI-отчёте — считает открытый [TimWeberRE100/Energy_Arbitrage_Model](https://github.com/TimWeberRE100/Energy_Arbitrage_Model) (Pyomo/CBC), в модуле `RoiPayback.tsx`/`ReportingService` сейчас не выводится.
6. **Аудит по каждому решению, а не только по дню** — Data Audit сейчас показывает покрытие источников по дате; DYNVOLT логирует "цену, прогноз, SoC и ограничения, которые привели к этому решению" на каждый час — для лендера/страховщика. Естественное расширение уже существующей страницы Data Audit.
7. **Панель "что если" для диспетчера** — пересчёт MILP на изменённом допущении (сценарий цены, поправка генерации, тариф) без сохранения — чисто UI-надстройка над уже существующим оптимизатором, как у Ascend SmartBidder.

**Статус на 2026-07-31 (после реализации и честной проверки):**
- **Пункт 1 (РДН+ВДР co-оптимизация) — реализовано и ОТКЛОНЕНО от прода.** `milp_model.py::optimize_battery_schedule_dam_idm` — рабочая двухступенчатая MILP (ступень 1 на РДН как раньше, ступень 2 — коррекция в пределах `idm_headroom_fraction` по цене ВДР). Оракульный бектест на 300 реальных днях (`scratch/backtest_dam_idm.py`, реальные факт-цены ВДР задним числом — лучший из возможных случаев): прирост всего **+0.4% при headroom=0.3, +1.2% даже при headroom=1.0** (неограниченно). ВДР в Украине, судя по реальным данным, слишком коррелирует с РДН структурно, чтобы давать заметный ДОПОЛНИТЕЛЬНЫЙ арбитраж поверх чистого РДН-оптимизатора для актива такого размера (250кВт/1МВт·год). Функция в коде, к продовому диспетчеру не подключена — см. полный разбор в докстрінгу функции.
- **Пункт 4 (ансамбль прогнозных моделей) — проверено бэктестом и ОТКЛОНЕНО, статус переоценён дважды.** Изначально (2026-07-31, старый leaky бектест) — сигнал по last_7d/last_30d нестабилен и разнонаправлен между `ensemble_average`/`ensemble_weighted`. Переоценка 2026-08-21 (Фаза C, leakage-fix, но БЕЗ as-of-унификации) выглядела устойчивее — last_30d улучшился на 17% для обеих схем. **Финальная честная переперепроверка 2026-08-25 (as-of-унификация + пост-Kyiv/UTC-фикс, CLAUDE.md п.36) — вывод Фазы C оказался артефактом нечестного бектеста**: на прод-эквивалентном пути (`build_forecast_feature_matrix(..., as_of=day, ...)` + `clip_and_shift`, тот же путь, что и solo-lightgbm) last_30d ансамбля стал ХУЖЕ на ~9-10%, осталось лишь ~3% выигрыша в среднем mean_wape. Solo LightGBM остаётся продовой моделью. Скрипты сравнения — `scratch/backtest_ensemble.py` (оригинал), `scratch/backtest_phase_c.py` (Фаза C, устарел методологически), `scratch/backtest_phase2_ensemble_asof.py` (финальный честный прогон).
- **Пункт 2 (кусочно-линейная деградация вместо плоской константы) — реализовано 2026-08-24.** `milp_model.py::tiered_degradation_rates` — 2-тиерная выпуклая кривая, якорь — реальные данные Preger et al. 2020 (Sandia, J. Electrochem. Soc., LFP-ячейки, монотонное падение цикл-жизни с глубиной разряда, 2500-9000 EFC). Калибровка сохраняет текущий `Asset.deg_cost_per_mwh` как средневзвешенное при полном использовании `max_cycles_per_day` — не меняет существующую финансовую шкалу, только форму. Честный бектест на 300 реальных сутках (`scratch/backtest_degradation_tiers.py`): дней с >1 циклом 19→13, средняя деградация -21% (577.81→455.34 грн/добу), средняя годовая прибыль +7.36% на тех же ценах. Подробности и статус деплоя — CLAUDE.md п.29.
- **Пункт 3 (% захваченной прибыли от идеального прогноза) — реализовано.** `forecast_accuracy.py::compute_real_profit_capture_ratio` — честный финансовый расчёт (не проксі через WAPE, как было раньше): реальный P&L выполненного диспетчерского плана (`ChargeDischargePlan`), пересчитанный по РЕАЛЬНОЙ цене дня, делённый на то, что дал бы MILP, если бы знал реальную цену наперёд (`optimize_battery_schedule` на факт-ценах). `get_profit_capture_ratio` теперь пробует этот реальный расчёт первым, и только если данных мало — откатывается на старый WAPE-проксі (как раньше). Новый источник `real_dispatch_vs_perfect_foresight` добавлен в `ForecastAccuracy.tsx`. **Важная находка при тестировании**: без защитной проверки на соответствие текущим лимитам актива (`Asset.power_mw`/`capacity_mwh`) получался физически невозможный ratio >1 (реальный факт "заработал" больше, чем теоретический максимум) — оказалось, старые локальные `ChargeDischargePlan` посчитаны для актива ~1МВт/~4МВт·год, а текущая настройка в БД — 250кВт/1МВт·год (конфиг менялся). Добавлена проверка, пропускающая дни с несовпадающими лимитами (`skipped_infeasible_days` в ответе) — на локальной dev-БД из-за этого сейчас недостаточно валидных дней (откатывается на WAPE-проксі), должно заработать на VPS/при накоплении истории со стабильным конфигом актива.

**Дольше горизонт / требует регуляторной готовности (не сейчас, но зафиксировать):**
- Co-оптимизация арбитража + резервов/балансирующих услуг в одном MILP (открытые [thibault-charbonnier/arbitrage-reserve-cooptimization](https://github.com/thibault-charbonnier/arbitrage-reserve-cooptimization), [RemiBGT/Battery-CoOptimization-Arbitrage-Reserve-Markets](https://github.com/RemiBGT/Battery-CoOptimization-Arbitrage-Reserve-Markets), французские данные) — напрямую перекликается с уже отмеченной в §7 темой агрегаторов/балансуючих груп в Украине (KNESS Energy и регуляторка). Пока нет доступа BESS к этому рынку в Украине — просто зафиксировано как направление.
- **Штраф за небаланс у цільовій функції MILP (з зовнішнього ревью 2026-08-24) — заблоковано відсутністю реальних даних, перевірено.** Реальні погодинні ціни небалансу технічно існують (Укренерго MMS, особистий кабінет учасника ринку — `Розрахунок → Акаунти → Деталі акаунтів → Рахунок небалансу електричної енергії`), але доступ до кабінету не підтверджено з цієї сесії. Публічні джерела перевірені і відхилені: `ua.energy` (сторінки БР/небалансів) — жорсткий WAF-блок на автоматичний доступ (і curl, і WebFetch, `403`); сторонній портал energy-map.info — має реальний робочий каталог (РДН/ВДР індекси України та сусідніх PL/RO/SK/HU, погодинний баланс потужності по типах генерації до 27.10.2022, середньозважені ціни РДН — потенційно корисно окремо для HUPX/OKTE-фіч або продовження вікна `GenerationAdjustment`, не зараз), але користувач підтвердив: датасет саме про балансуючий ринок/небаланси там **устарілий/уривчастий**, для честної моделі не годиться. Висновок: без реального свіжого джерела штраф за небаланс НЕ реалізовувати (вигадані ставки порушили б головний принцип проєкту) — відкладено до появи реального доступу (MMS-кабінет учасника ринку або новий публічний датасет).
- Портфельная/VPP-оптимизация нескольких активов (AutoGrid Flex — 8ГВт/9 стран) и полностью автоматическая подача заявок с расчётами (Gridmatic) — отклонено как нереалистичное сейчас: нет ни парка из нескольких активов, ни API автоматической подачи заявок на украинском рынке.

**Не подтвердилось как явное улучшение:** RL-диспетчеризация (открытые [masa2203/battery_arbitrage_with_drl](https://github.com/masa2203/battery_arbitrage_with_drl), [ekahorsu/battery-arbitrage-reinforcement-learning](https://github.com/ekahorsu/battery-arbitrage-reinforcement-learning)) — во втором проекте честное сравнение на held-out данных показало DQN лишь незначительно лучше простой rule-based эвристики ($1845 vs $1778, "узкий и нестабильный от прогона к прогону" разрыв). Это подтверждает: MILP+хороший прогноз — не очевидно хуже RL для одного актива, менять текущий подход не за чем.

**Референс без прямого действия:** [OpenEMS](https://github.com/OpenEMS/openems) (1.5k★, LF-adjacent, реальные Modbus/MQTT-драйверы для BYD/Pylontech/Fenecon и др.) — на порядок более зрелый слой реального SCADA/железа, но без прогноза цены и биддинга вообще. Полезен как референс, если/когда smartbess-ems перейдёт от симулятора к реальному железу — не сейчас.

## 8. OREE — реальные правила ринку РДН/ВДР и видение будущей API-інтеграції (исследование 2026-08-06)

По прямой просьбе пользователя изучены официальные документы `oree.com.ua` перед тем, как продолжать развитие в сторону реальной автоматизации подачи заявок. Никакого кода в этой сессии не менялось — только исследование и фиксация понимания, roadmap на будущее. Полный план/находки: `/home/oleg/.claude/plans/sunny-doodling-rabbit.md` (локальный файл плана, не в git).

**Первичный документ**: «Правила ринку "на добу наперед" та внутрішньодобового ринку», діючі, затв. постановою НКРЕКП від 14.03.2018 №308 (в ред. від 24.06.2019 №1169, зі змінами по 02.05.2023 №832) — скачано `oree.com.ua/index.php/web/10648`, прочитано полностью (100 стр., PDF→текст через `pypdf`, установлен `pip3 install --user --break-system-packages pypdf` за отсутствием poppler-utils/venv в окружении). **Осторожно**: на сайте лежит также устаревший «Проект від 20.10.2017» (`DAM_IDM_Rules_DPE_v20_10_17.pdf`, 75 стр.) — не действующий, легко перепутать по похожему названию.

Ключевые факты (первичный источник, не выдумано):
- **Закриття воріт РДН — 12:00** доби, що передує постачанню (ОР може перенести, не пізніше 21:00). Заявки — за 7 календарних днів до постачання і до закриття воріт.
- **ВДР** — подача з **15:00** попередньої доби (перенесення не пізніше 22:00), безперервні торги, закриття воріт — **за 60 хв до кожного розрахункового періоду** (ковзний дедлайн погодинно, не єдиний момент).
- Ціни заявок: **10.00–50000.00 грн/МВт·год**, крок 0.01, без ПДВ. (Проектний `PRICE_CAP=16000.0` у `ml_pipeline.py` — бізнес-припущення моделі, не юридична межа — не плутати.)
- Кожна заявка підписується **КЕП** уповноваженої особи — не просто API-ключ, а електронний підпис конкретної людини/токена.
- Обов'язковий **escrow-рахунок** з достатнім залишком коштів ДО подачі заявки (перевіряється автоматично).
- Реєстрація: заява → 2 робочих дні розгляду ОР → типовий договір про участь + окремі договори купівлі-продажу на РДН/ВДР.
- Типи заявок: погодинні, блочні (прості/профільовані/пов'язані до 3 рівнів), гнучкі.
- **Тарифи 2026 (`oree.com.ua/index.php/newsctr/n/30795`)**: фіксований місячний платіж **4669.71 грн** (без ПДВ) + тариф на операції **6.88 грн/МВт·год** (без ПДВ), сплата щоденно за фактом торгів — реальна операційна вартість для маленького 250 кВт BESS, варто врахувати в майбутній економіці автоматизації.

**Важна знахідка — ринок двосторонніх договорів (РДД) НЕ є миттєвим fallback**: загальні «Правила ринку» (постанова НКРЕКП №307 від 14.03.2018, `zakon.rada.gov.ua/laws/show/v0307874-18`) визначають РДД як окремий, довгостроковий OTC-механізм — учасники заздалегідь домовляються і реєструють обсяги («сальдована позиція»), що потім слугує підтвердженням/забезпеченням для великих заявок на продаж на РДН. Це НЕ спот-механізм «заявка не зіграла → продай прямо зараз кому завгодно» — для маленького активу з щодня різним обсягом небалансу знайти контрагента на щоденні спот-угоди по РДД нереалістично як автоматичний процес. Практичний висновок: якщо потрібен автоматичний fallback при невиконанні заявки РДН — реалістичний шлях це автоподача залишку на ВДР (те, що вже частково спроектовано як порада диспетчеру через `estimate_idm_price_for_hour`, див. §1a), а не РДД.

**Технічна платформа для майбутнього API**: OREE використовує **XMTRADE|PXS** — брендована реалізація вендорської платформи **XMtrade/ISOT** (та сама, що й у словацького оператора ринку OKTE — `okte.sk/en/api-documentation/`). У OKTE ця платформа документує REST+WebSocket API (створення/зміна/скасування заявок, orderbook, ринкові дані реального часу), автентифікація — клієнтський сертифікат + basic auth, доступ надається зареєстрованим учасникам за окремою угодою. Публічної документації API саме для OREE не знайдено — служба підтримки (`support.oree.com.ua/knowledgebase.php`) покриває лише браузер/Excel-завантаження заявок і проблеми з КЕП — але з огляду на спільного вендора, приватний API майже напевно існує і видається зареєстрованим учасникам за окремим запитом, не публікується самостійно.

**Статус рішення користувача (2026-08-06)**: доступу в кабінет OREE поки немає, автоматична подача через API — справа майбутнього, не термінова задача. Зараз і ще довго диспетчер продовжує вносити цифри вручну; програма при цьому не пасивна — вона «керує процесом» (прогноз+MILP → аналіз точності → готова пропозиція диспетчеру через `generate_bids_for_date`), що вже реалізовано і працює. Roadmap на майбутнє (коли з'явиться доступ): абстракція `oree_client` (Mock/XmtradeOreeClient за фіче-флагом) → розширення `MarketBid` полями реальної подачі (`external_order_id`/`submitted_at`/`oree_submission_status`) → реальна автоподача з dry-run за замовчуванням → fallback на ВДР замість поради. Деталі — у файлі плану вище.

**Реалізовано без API (2026-08-06, продовження, уточнено)**: `oree_client`-абстракцію (навіть Mock) користувач свідомо відклав на майбутнє («будемо пізніше»), натомість реалізовані 4 конкретні поліпшення на основі вже вивчених фактів вище, без жодного звернення до API OREE:
1. **Легальні межі ціни заявки** (10–50000 грн/МВт·год) тепер клипаються в `generate_bids_for_date` (`clamp_bid_price_to_oree_bounds`), з UI-попередженням у таблиці заявок.
2. **Реальні тарифи 2026** (4669.71 грн/міс + 6.88 грн/МВт·год) додані окремим рядком у `ReportingService.calculate_project_economics`/`get_executive_summary_report`, `RoiPayback.tsx`, `ExecutiveOverview.tsx` — НЕ заміняючи, а доповнюючи существующую евристику опексу.
3. **Live countdown** до 12:00 (РДН) і ковзних 60-хвилинних воріт ВДР — новий компонент `BidGateCountdown.tsx`, чиста клієнтська `Date`-арифметика в київському часі (`Intl.DateTimeFormat`).
4. **Синтезований «центр дій» диспетчеру** (`build_daily_action_summary`, ендпоінт `/bids/action-summary`, компонент `BidActionCenter.tsx`) + Telegram-нагадування (`check_and_send_bid_reminder`, джоба 10:00, dedup за змістом дій) — ОБИДВА тільки ЧИТАЮТЬ вже наявні `MarketBid`, ніколи не генерують/не подають заявки самі.

Жодних нових таблиць/колонок БД — усі нові поля обчислюються на льоту або в JSON-кеші з self-heal бэкфиллом. Перевірено локальним HTTP-циклом і задеплоєно на VPS з реальними запитами (`oree_participation_fee_ytd_uah: 43442.64` на реальних 217 днях прод-даних). Детальна хронологія — CLAUDE.md п.18.
