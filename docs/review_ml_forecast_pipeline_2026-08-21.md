# Review: ML forecast pipeline — методологические проблемы (2026-08-21)

Получено от пользователя 2026-08-21 (внешнее ревью, по образцу `CODE_REVIEW.md`/`message.txt` от того же дня, но фокус на `src/modules/forecast_service/ml_pipeline.py` и смежных модулях). **Отложено до завершения Этапа 1** (security + честность интерфейса, см. `CODE_REVIEW.md`) — зафиксировано здесь как следующий этап, не начато.

Главный тезис: проблема не в гиперпараметрах LightGBM — обучение, backtest и production-инференс решают разные задачи, поэтому исторические метрики (WAPE и т.д.), на основе которых в MEMORY.md принимались решения о фичах/ensemble/lag, могут не отражать реальную точность в проде.

## Что не так (построчно проверенные находки автора ревью, не перепроверено нами)

1. **Утечка будущих данных** — `prepare_features()` делает `bfill()`/интерполяцию сразу на всей истории (`ml_pipeline.py:139-172`), включая сам target Price.
2. **Backtest ≠ production inference** — backtest использует `prepare_features()`, прод — отдельную `build_forecast_feature_matrix()` (`ml_pipeline.py:642-708, 807-987`), с разной логикой погоды/IDM/пропусков/ручных корректировок.
3. **Погода не привязана к target-дате** — `fetch_weather_forecast()` всегда грузит «завтра» относительно сервера (`forecast.py:17-28`, `data_manager.py:523-559`), сопоставление по `iloc[h]`, а не по timestamp (`ml_pipeline.py:909-912`).
4. **Backtest использует архивную погоду вместо прогноза** — офлайн-метрики оптимистичны.
5. **Смешаны UTC/Kyiv/локальное время контейнера** — OREE naive Kyiv, ENTSO-E UTC без tz, Open-Meteo без явной tz → возможен сдвиг 2-3 часа.
6. **Не учтён момент публикации данных** — backtest считает `IDM_Price_Lag_24`/ENTSO-E доступными по event timestamp, хотя публикуются с задержкой (IDM — одна из главных фич, `ml_pipeline.py:97-105`).
7. **Модель сильно зависит от вчерашней цены** (`Price_Lag_24/48/168`, IDM, rolling means, `ml_pipeline.py:81-129`) — плохо предсказывает аварии/обстрелы/резкие ограничения импорта/price floor-cap/внезапный солнечный профицит/смену режима рынка.
8. **Пропуски — правдоподобные выдуманные значения** (синтетическая погода, fallback-константы: `data_manager.py:421-434, 563-579`; `ml_pipeline.py:861-867`).
9. **Live-метрики можно улучшить задним числом** — forecast перезаписывается, `generated_at` реально не сохраняется (`forecast.py:61-75`) — перекликается с п.9 из `CODE_REVIEW.md`.
10. **P10/P90-калибровка не для той модели, что развёрнута** — quantile-модели переобучаются на всех данных после расчёта correction (`ml_pipeline.py:393-440`), формальная split-conformal гарантия не сохраняется.
11. **Backtest и production — разная постобработка** — прод применяет clipping+ручной shift (`ml_pipeline.py:1022-1030`), backtest оценивает raw predictions (`ml_pipeline.py:702-708`).
12. **В этом checkout нет текущих артефактов модели** (`metrics_report.json`, `backtest_report.json`, `conformal_calibration.json`, `.pkl`) — фактическую точность/provenance по одному workspace не проверить.

## Что исправить сначала (по автору ревью)

1. Единственный **as-of feature builder** для production и backtest — принимает дату+время выпуска прогноза, target intervals, только опубликованные к этому моменту данные.
2. Убрать утечку: не интерполировать target, дропать строки без target, отказаться от `bfill`, фичи — только предыдущими значениями, ограничить длину gap, добавить `is_missing`/`data_age_hours`.
3. Погода: передавать `target_date`, `timezone=Europe/Kyiv`, join по timestamp а не `iloc`, отклонять прогноз при нехватке часов, архивировать реально использованный weather forecast + issuance time.
4. Единая модель времени: физический timestamp в UTC, отдельно OREE delivery date/period, конвертация в Europe/Kyiv, тесты на DST и 23/25-часовые дни.
5. Неизменяемые прогнозы: `ForecastRun.id`, `generated_at_utc`, `target_date`, `data_cutoff`, hash модели/данных, raw + postprocessed prediction отдельно, ручная поправка отдельно.
6. Переписать walk-forward так, чтобы буквально вызывал production feature pipeline и production clipping.

## После исправления методологии

- Сравнить окна обучения (вся история / 24мес / 12мес / 6мес) — рынок 2021 и 2026 слишком разный для expanding window.
- Regime-фичи, известные до закрытия рынка (price caps, пропускная способность, ремонты, прогноз нагрузки, grid-stress/Telegram — только с publication timestamp).
- Улучшить weather representation (несколько регионов, capacity-weighted для СЭС/ВЭС, окремі зони).
- Проверить двухступенчатую модель для price-floor событий (классификатор + отдельная регрессия), включать только при устойчивом улучшении на нескольких окнах.
- Drift monitoring: WAPE/bias 7/30/90 дней, skill vs lag-24/lag-168, feature drift, доля missing/stale, P10/P90 coverage, profit regret MILP.

## Как честно измерять улучшение

Global WAPE, MAE, signed bias, WAPE по часам/режимам, skill относительно Price_Lag_24/168, P10/P90 coverage + средняя ширина интервала, прибыль фиксированного графика к perfect foresight, CI разницы старой/новой модели. **MAPE не использовать как основную метрику** (при цене ~10 грн — огромная и малоинформативная). Минимальный честный горизонт: 12 месяцев walk-forward, отдельно последние 90 дней/выходные/floor-cap/вечерний пик.

**Важно**: offline WAPE после исправления утечки/oracle-погоды скорее всего сначала **ухудшится** — это ожидаемо и означает, что раньше метрика была завышена, а не что модель стала хуже.

## Вторая часть: почему модель структурно ограничена (не баг, а потолок point-forecast подхода)

Модель авторегрессионная (главные фичи — `Price_Lag_24/48/168`, IDM) — хорошо продолжает привычный профиль, но не видит скрытые для системы факторы: реальные заявки участников аукциона, доступность генерации, стратегии крупных продавцов, аварии/обстрелы. Большая часть этого публично недоступна до аукциона.

Практический вывод автора: не ставить задачу «точно угадать цену часа», а (a) предсказывать профиль дня, (b) находить дешёвые/дорогие часы, (c) оценивать вероятность экстремума, (d) честный P10-P90, (e) устойчивый к ошибке график, (f) дать диспетчеру возможность добавить информацию, которой нет в открытых источниках.

Рекомендации: добавлять сигналы, известные до аукциона (нагрузка, ремонты, пропускная способность импорта, Укренерго, grid-stress, прогноз ВИЭ); структурировать ручные события диспетчера (не просто %, а «минус 500 МВт АЭС» и т.п.); отдельный классификатор «аномальный день» → расширять P10-P90 при риске; мерить точность отдельно на обычных/шоковых днях; не сжимать неопределённость в одно число — показывать базовый/дефицитный/профицитный сценарии.

## Статус

**Фаза A реализована (2026-08-21)** — фундамент, аддитивно, без изменения текущих предсказаний:
- Явные таймзоны: OREE (DAM+IDM) теперь явно конвертируется Kyiv→UTC при приёме (`fetch_oree_market_month`), Open-Meteo получает явный `&timezone=UTC` (проверено живым запросом — совпадает с прежним дефолтом, реального пересчёта нет), ENTSO-E не менялся (уже был корректен). **Только для новых данных — уже накопленная история (CSV-кеш, БД, `realized_profit_uah`) НЕ пересчитана задним числом** (решение пользователя, 2026-08-21).
- `ForecastRun`/`ForecastRunHour` — неизменяемая история запусков прогноза (append-only, `generated_at_utc` — реальное время генерации), пишется дополнительно к `PriceForecast` (её контракт не менялся). `compute_rolling_accuracy` теперь реально фильтрует по `generated_at_utc < timestamp` для дат с новой историей, с фолбэком на старый путь для более ранних дат.
- `WeatherForecastArchive` — архивирует реально использованную прогнозную погоду (включая честную маркировку `synthetic_fallback`) на каждый вызов `/forecast/run`/ночной джобы — начало накопления данных для будущего honest backtest на прогнозной (не архивной) погоде.

**Фаза B реализована (2026-08-21, тем же вечером)** — единый as-of feature builder, устранение утечки, переписан `walk_forward_backtest` на вызов production-пайплайна, фикс калибровки P10/P90:

- Новый модуль `src/modules/forecast_service/feature_pipeline.py` — единственное место, где теперь живе побудова ознак (`FEATURES`, `build_training_table` — наступник `prepare_features`, `build_asof_feature_matrix` — наступник `build_forecast_feature_matrix`, `clip_and_shift`, `_get_generation_adjustment`/`_get_reference_capacities_mw`/`_get_baseload_passthrough_ratio`/`_get_price_shift_pct`).
- **Утечка устранена**: `build_training_table` больше не робить `interpolate(method='linear')`/`.bfill()` по всій історії одразу (навіть без явного `.bfill()` лінійна інтерполяція вже дивиться в обидва боки для внутрішніх дірок — теж утечка). Тепер: target `Price` взагалі не заповнюється (дірки — чесний `NaN`, рядок відсіюється фінальним `dropna`); ознаки — `ffill(limit=MAX_CAUSAL_FFILL_GAP_HOURS=6)`, лише минулим значенням. На реальних даних (2026-08-21): 49411 сирих рядків → 48965 чистих (відсіяно ~0.9%, чесно, без вигаданих значень).
- **as_of-параметр + симуляція публікаційної затримки**: `build_asof_feature_matrix(target_date, forecast_weather, last_prices, as_of=None, apply_manual_overrides=True)` — для живого проду (`as_of=None`→`datetime.utcnow()`) поведінка байт-в-байт як раніше. Для бектеста (`as_of=симульований історичний момент`) хвіст `IDM_Price`/`Grid_Net_Export_MW` в `hist_before_target` явно затирається в `NaN` за `IDM_PUBLICATION_DELAY_HOURS=24`/`ENTSOE_PUBLICATION_DELAY_HOURS=6` годин до `as_of`, ПЕРЕД тим же відновленням форми хвоста (медіанний DAM-IDM спред), що вже давно перевірено в проді — інакше історична дата "знала б" наперед те, чого прод реально не бачив у той момент.
- **`walk_forward_backtest` реально викликає `build_forecast_feature_matrix`** (та сама функція, що й `predict_next_day`/`predict_price_band`) для конфігурації, що відповідає проду (`model_type='lightgbm'`, без `use_surplus_classifier`/`extra_features`) — `summary['methodology_version'] == 'phase_b_asof_unified_2026'`. Інші конфігурації (ensemble/surplus/extra_features — немає прод-еквіваленту, з яким уніфікувати) лишились на старому зрізовому шляху, лише з виправленою утечкою (`methodology_version == 'phase_b_leakage_fix_only_2026'`).
- **`acknowledge_approximation=True` обов'язковий** для `weather_mode='archived_actual_approx'` (типово) — інакше `ValueError`, як і вирішив користувач. `weather_mode='archived_forecast'` бере реально видану погоду з `WeatherForecastArchive` (Фаза A) — для більшості історичних днів поки немає покриття (архів лише почав накопичуватись 2026-08-21), такі дні чесно пропускаються (`skipped_days_no_weather_archive`), не підміняються мовчки.
- **Калібрування P10/P90 виправлено**: `train_quantile_models` більше НЕ перенавчає `lower_final`/`upper_final` на всіх даних — продові `.pkl` це САМЕ `lower_model`/`upper_model`, чесно навчені лише на `df_train` (без `df_calib`), на яких і порахована conformal-поправка. Формальна split-conformal гарантія покриття тепер реально виконується для розгорнутої моделі. Перевірено реальним прогоном: `coverage_after_conformal_correction: 0.8007` (≈ target 0.8).
- `quantile_coverage_backtest` — торкнуто мінімально (той самий gate + `build_training_table`, БЕЗ as-of-уніфікації): функція не має жодного виклику ніде в застосунку, повна уніфікація не мала кого виправляти.

**Перевірено локально реальними прогонами** (не лише синтаксис): `build_training_table` на 49411 реальних рядках — 0 NaN у FEATURES/Price; `walk_forward_backtest(test_days=5, acknowledge_approximation=True)` — повний прохід, `methodology_version` підтверджує новий шлях, `n_hours: 24` на кожен день; `predict_next_day`/`predict_price_band` на реальну завтрашню дату — санні числа, `lower<=upper` тримається; `train_quantile_models()` — реальне перенавчання, коректне покриття; повний `train_models()` (LightGBM+XGBoost+MLP) — 499с, WAPE 22.57% (в межах задокументованого діапазону 22-26%, нічого не зламано).

**Не зроблено (Фаза C, окрема сесія)**: повторна перевірка ~4 історичних рішень (Lag_48, EU_DAM_Price, PL/RO погода, ensemble/recency weighting), що всі показували підозрілий патерн "mean_wape краще, last_7d/30d гірше" — тепер, коли бектест реально відповідає проду, варто перевірити, чи це був артефакт старого leaky бектеста, а не справжня знахідка. Повний прогін `walk_forward_backtest(test_days=90, acknowledge_approximation=True)` для порівняння з задокументованим базлайном (22-26% WAPE) теж не зроблений у цій сесії (5-денний тест — лише перевірка механізму, не статистично значущий прогін) — рекомендується перед тим, як цитувати нові цифри як остаточні.

Знахідки самого ревью (13 пунктів вище) перепроверені построчно трьома паралельними агентами 2026-08-21 проти актуального коду — підтверджені, місцями гірше, ніж описано спочатку (див. історію сесії/CLAUDE.md п.20-21 за точні деталі).
