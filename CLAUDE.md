This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Этот файл — точка входа для продолжения разработки SmartBESS EMS в новой сессии (после обрыва/потери контекста). Второй такой файл — [MEMORY.md](MEMORY.md) в этой же папке: там фичи/UI/эксперименты с прогнозом/планы/рыночное исследование. Читать оба перед началом работы.

**Эти два файла должны обновляться при каждом значимом изменении проекта** (новая/изменённая фича, решение по расчёту, изменение UI-конвенции, проверенный вариант прогноза, деплой, план) — не откладывать до следующей сессии. Хук только напоминает — реально переписывает файлы каждый раз ассистент, не автоматика; если изменение не документируемое, напоминание можно просто проигнорировать.

## Что это

SmartBESS EMS — платформа для украинского BESS-накопителя, зарабатывающего на арбитраже цен рынка на добу наперед (РДН/DAM): прогноз цены (ML) → MILP-оптимизация графика заряд/разряд → диспетчеризация → SCADA-симуляция → финансовая отчётность для инвестора. Домен: Україна, `oree.com.ua` (Оператор ринку) как основной источник цен.

## Стек и структура

- Backend: FastAPI + SQLAlchemy, `app.py` — вход, `uvicorn app:app`, порт 5000 по умолчанию.
- Frontend: React 19 + Vite + TS в `frontend/`, роли Viewer/Operator/Manager/Admin, два воркспейса: **Dispatcher Console** (оперативная работа) и **Director Dashboard** (инвестор/руководитель).
- БД: sqlite локально (`data/smartbess.db`), Postgres/TimescaleDB в docker-compose для прод-подобного окружения. Схема — `Base.metadata.create_all` (`src/database/init_db.py`), без Alembic — новая модель применяется просто рестартом приложения.
- Ключевые модули backend:
  - `src/modules/forecast_service/ml_pipeline.py` — прогноз цены (LightGBM/XGBoost/MLP + LightGBM quantile P10/P90).
  - `src/modules/optimization_service/milp_model.py` — PuLP/CBC MILP-оптимизация графика батареї + Monte Carlo VaR.
  - `src/modules/market_data_service/data_manager.py` — сбор/кэш реальных данных (`oree.com.ua`, Open-Meteo).
  - `src/modules/external_data_service/` — `entsoe.py` (трансграничные перетоки + цена соседних зон), `intraday_market.py` (ВДР/IDM с oree), `gas_price.py` (index.minfin.com.ua), `telegram_public.py`/`telegram_bot.py` (публичные посты Укренерго/Мінэнерго как сигнал грид-стресса + алерты, теперь также нагадування по заявках), `neighbor_weather.py` (погода PL/RO).
  - `src/modules/scada_service/` — симулятор Modbus-телеметрии + `soc_state.py` (цепочка приоритетов для стартового SoC).
  - `src/modules/bidding_service/services.py` — реальний механізм подачі заявок РДН (аукціон єдиної ціни), легальні межі ціни OREE, синтезований «центр дій» диспетчеру (`build_daily_action_summary`).
  - `src/tasks/scheduler.py` — ежедневная джоба 06:00 (перенесена с 17:30 2026-08-04 — см. хронология): sync данных → прогноз (LightGBM) → P10/P90 → MILP → сохранение плана. Это чистый инференс — модель НЕ переобучается этой джобой, используется уже обученный `.pkl` с диска. Отдельная ночная джоба (02:00, п.15) переобучает модель. Новая джоба 10:00 (п.18) — Telegram-нагадування про заявки.

## Как запускать/тестировать локально (грабли уже найдены — не наступать заново)

**Команды:**
- Полный стек (реальная прод-подобная проверка, предпочтительно): `docker compose up --build -d` — поднимает `smartbess-db` (TimescaleDB/Postgres :5432), `smartbess-redis` (:6379), `smartbess-platform` (FastAPI+собранный фронтенд :5000/5004, SCADA Modbus :5020). Изменение бэкенд-файла требует `docker cp` + `docker restart` (hot-patch) или `docker compose build && up -d` (постоянно) — см. «Деплой / VPS» ниже, `src/` не bind-mounted.
- Бэкенд вне контейнера (ad-hoc): `python3 app.py` или `uvicorn app:app` — см. «Стек и структура» выше про порт/зависимости.
- Frontend prod-сборка: `cd frontend && npm run build` (= `tsc -b && vite build`) — из-за WSL-проблемы с `node_modules` (см. ниже) в этой песочнице реально работает только через `docker compose build smartbess-platform` (собирает фронтенд внутри контейнера); на хосте — только через Windows `node.exe`, см. следующий пункт.
- Frontend typecheck (реально соответствует прод-сборке, не `tsc --noEmit`) — см. отдельный пункт ниже.
- Frontend lint: `cd frontend && npm run lint` (`oxlint`, конфиг `frontend/.oxlintrc.json`).
- Backend-тесты: файлы `test_*.py` в корне репозитория — смесь двух стилей. `test_bidding_service.py` — настоящие `pytest`-тесты с `assert` (`pytest test_bidding_service.py`, один тест — `pytest test_bidding_service.py::test_clamp_below_floor`). Остальные (`test_services.py`, `test_api_v1.py`, `test_scada_e2e.py`, `test_train.py`, `test_redis.py`) — печатают ожидаемое/фактическое без `assert`, задуманы для запуска напрямую (`python3 test_services.py`) и визуальной проверки вывода, не для CI. **Все тесты обращаются к реальной локальной БД (`SessionLocal`), не к изолированной тестовой** — открытый пробел проекта (см. «Открытые пункты»), учитывать при интерпретации падений.

- Бэкенд: системный `python3` (fastapi/sqlalchemy стоят через `pip --user`). **`.venv` в репозитории НЕ имеет нужных зависимостей** — не использовать.
- Порт 5000 часто занят посторонним процессом (`~/energo/energy-prediction-ua`, другой проект) — проверять `ss -ltnp` перед тем как считать что-то этим репо; для ad-hoc тестов бэкенда использовать другой порт (напр. 5050).
- Frontend dev-сервер (`npm run dev`/vite) в этом WSL-окружении не поднимается: `node_modules` собран под Linux, но реально доступен только Windows `node.exe`. Это давняя проблема окружения, не чинить переустановкой node_modules без явного запроса.
- **Проверка TS перед деплоем — только `tsc -b`, НЕ `tsc --noEmit`.** Проект использует составной tsconfig (`tsconfig.json` + `tsconfig.app.json`/`tsconfig.node.json` через project references), и реальная сборка (`npm run build` → `tsc -b && vite build`) применяет более строгие настройки, чем плоский `tsc --noEmit` по корневому конфигу. Найдено на практике 2026-07-31: `tsc --noEmit` прошёл чисто, а `docker compose build` на VPS упал с `TS18046 'r' is of type 'unknown'` (generic-функция без явного типа возврата резолвится в `unknown`, а не в `any`, в строгом режиме). Проверять командой `"/mnt/c/Program Files/nodejs/node.exe" node_modules/typescript/bin/tsc -b --force` (`--force` — чтобы не полагаться на инкрементальний кэш) — только она реально соответствует продовой сборке. **Ещё одна ловушка, найдена 2026-08-06 (п.18)**: `lucide-react`-іконки не приймають `title`-проп напряму (`Property 'title' does not exist on type ...LucideProps`) — обгортати в `<span title="...">`, якщо потрібен нативний tooltip на іконці.
- **Застаріло, виправлено 2026-08-24 (п.34)**: цей пункт раніше описував мок unsigned JWT (`alg: none`), зібраний на клієнті. Це вже не так — авторизація тепер підписаний HS256-токен через `POST /api/v1/auth/mock-login` (`src/api/v1/endpoints/auth.py`, секрет `MOCK_JWT_SECRET` ніколи не потрапляє в браузер) — частина ревью безпеки (CLAUDE.md, "Пункти 1-4 ревью безпеки"). Для curl: спочатку `POST /api/v1/auth/mock-login` з `{"role": "Admin"}`, узяти `token` з відповіді, потім `Authorization: Bearer <token>` — старий трюк з саморобним base64url `alg:none` токеном більше НЕ працює (`401 Invalid token format`).
- В коде/UI намеренно используется украинский язык (комментарии, докстринги, строки интерфейса) — это принятая конвенция проекта, не ошибка и не то, что нужно "исправлять".
- **`src/database/init_db.py` сам не импортирует `src.database.models`** — если писать standalone-скрипт (не через `app.py`), который вызывает `init_db()` напрямую, нужен явный `import src.database.models` ПЕРЕД вызовом `init_db()`, иначе новые ORM-классы не зарегистрированы в `Base.metadata` и `create_all` их не создаст (найдено 2026-08-06, п.18 — локальная sqlite не имела таблиц `market_bids`/`bid_margin_overrides`/`price_shift_overrides`, т.к. эти фичи разрабатывались сразу на VPS).

## Главный принцип проекта: никаких выдуманных данных

Явное правило по всему коду ("не вигадувати", "не приймається на віру", "чесно NaN"): реальные данные и честный NaN на пробелах — никогда не константа-затычка или `np.random`. Раньше почти все "рыночные факторы" (Nuclear_Gen, Gas_Price, VDR_Volume, Grid_Import_Export и т.д.) были синтетическим шумом — это была главная причина плохого прогноза, всё заменено на реальные источники (см. MEMORY.md, раздел "Источники данных"). Новая фича идёт в продовый `FEATURES` только после `walk_forward_backtest`, и результат (даже отрицательный) документируется комментарием в коде, а не тихо выбрасывается.

## Продакшн-модель прогноза

Основная модель — **LightGBM** (`scheduler.py` всегда использует `predictions['lightgbm']`; XGBoost/MLP считаются параллельно и доступны в ручном запуске `/forecast/run` через `selected_model`, но не являются продовым выбором). P10/P90-интервал — отдельная LightGBM quantile-регрессия со split-conformal калибровкою на последних 60 днях (заменил вымышленное допущение ±1.64σ в риск-сценариях MILP). Подробности по фичам/экспериментам — MEMORY.md.
